# ADR 0003: Explicit content-processing trust boundaries

**Status:** Normative product/security policy upon review and merge of #13; security controls described below are **not** implemented by this decision. The original default-deny baseline was accepted in PR #51. Owner product choices are recorded in [#50](https://github.com/berniemackie97/Praxis/issues/50).
**Scope:** Owner-local clients, self-hosted/remote installations, remote synchronization, collection sharing, derived knowledge, model inference, agent work and recovery. This is a *trust contract*, not a network endpoint, key-management service or cryptographic implementation.

## Decision: placement and processing are independent

Praxis supports multiple owner-configured deployments (fully local, self-hosted and remotely hosted) **without** granting any of them automatic access to private source content. Each **security space** has one effective processing boundary; a deployment may hold several independently protected spaces. Ownership, source provenance and operation-specific grants are independent from both the location of stored bytes and the location of a model.

| Collection boundary | Who may hold plaintext / decrypting keys | What a remote host may do | Residual exposure |
| --- | --- | --- | --- |
| **Local-only** | Explicitly authorized local OS-user process and its approved local devices | No original, derived, index, backup, content-based identifier or source metadata upload; no remote sync | Local catalog/originals are currently plaintext and depend on host filesystem isolation; malware running as the owner is in scope as a limitation |
| **Client-held encrypted sync** | Authorized clients holding collection decryption keys, including separately enrolled sharing recipients | Authenticate, store/relay opaque ciphertext, order operations, enforce quotas, device/collection grants and protocol-visible revision/conflict metadata; **cannot** independently index or run plaintext agents | Service learns permitted routing/size/timing/event metadata; compromised authorized endpoints and historical downloaded copies remain risks |
| **Trusted-host processing** | Enrolled clients and explicitly selected processing service(s) holding authorized decrypting authority | Read the specified collections, index and run approved background processing even while client devices are offline; disclosure to *another* model or provider still needs independent consent | Authorized host/operator compromise exposes plaintext and derived material; **not end-to-end encrypted** |

These are **security classes**, not three switches that can be freely toggled on individual records. Each security space's authoritative owner, class, key epoch, processing grants and share membership must be consistent across manifest, original objects, revisions, sync, cache, search, backups and derived knowledge. An untrusted client cannot grant itself a higher class/authority merely by changing a request field. Unknown class/version or absent grant fails closed.

**Security spaces are not organizational collections.** Existing `source_collections` and `source_collection_memberships` (ADR 0023) are **many-to-many owner-created organizational views**. Creating, renaming, archiving or adding a source to such a collection must **never** grant access, change its processing class or copy its key. Each authoritative source and its revisions are assigned to **exactly one security space** for access, storage and encryption; a cross-space copy is a separately authorized import with distinct source identity and traceable provenance, never a second security owner for the same mutable source record. Organizational views may group sources from multiple spaces, but every list, count, source fetch, search, derived result, inference request and agent action must filter by the caller's space/source grants at execution. Physical identical-byte object deduplication is an internal optimization only; it must not expose cross-space existence, keys or access, and cannot collapse logical source ownership. ADR 0006's remote `collectionId` must identify the authoritative synchronization **security space**, not the existing UI grouping UUID; #15/#19 own the real schema and migration validation. This separation is an implementation prerequisite for household/multi-user mode, not an already-present catalog feature.

**No implicit class transition.** Moving from local-only to remotely stored or from client-held ciphertext to trusted-host plaintext requires a separately authenticated owner approval, an explicit destination and fresh authorization/grant issuance, versioned data transfer and review of derived indices, device keys and backups. A switch back to client-held mode is **not retroactive secrecy**: plaintext that a trusted host previously saw, historical backups and downstream provider disclosures must be inventoried and processed under explicit retention/deletion policy. Until an audited migration exists, reject in-place class changes and use a deliberate new-collection import/export. Never silently upload local-only bytes, silently downgrade encryption or reuse indexes across classes.

## Principals, device identity and sharing

- An **account/principal** represents an authorized person. A **device identity** is a separately enrolled proof-of-possession key bound to that principal and the selected deployment; an **integration/agent identity** is a separate, narrowly scoped caller. Collection, record, revision, source, device and operation UUIDs are not credentials. Principal, device/session and resource grant must all be valid at request time.
- For a networked deployment use a standards-based authenticated identity provider/issuer. Native clients use system-browser authorization-code with PKCE when OAuth/OIDC is selected; the server validates issuer/audience/expiry and binds sessions to the enrolled device, with token rotation and revocation. The owner/local process policy in [ADR 0021](0021-owner-local-caller-security.md) is separate and does not automatically authorize remote requests. The exact self-hostable issuer, device key attestation/proof and supported browser/mobile flows are acceptance decisions for #15; no mandatory paid identity vendor.
- An owner may explicitly grant a security space to another person or a household group with allowed operations. Every original/read, revision, attachment, event, list count, query, snippet, cached answer, inference context and background action is authorized against the **requesting** principal and current membership—not merely the owner's grant or the content digest. Default is private. Revocation denies new service operations and access to future keys promptly; it **cannot erase copies already delivered** to an offline device or third party.
- In a client-held encrypted security space, a member must additionally receive its decrypting key through an authenticated, end-to-end wrapped key distribution from an authorized client (or separately guarded owner recovery material). Membership on the server **alone cannot give the server plaintext**. Removing a member requires forward key rotation for newly protected versions; historical versions copied earlier cannot be made secret retroactively.
- The first-party local UI has the owner-local boundary from ADR 0021. The current SwiftUI host uses a child .NET worker over inherited pipes rather than the originally proposed in-process call path: #215/#107 must verify actual child-process privileges, inherited-handle isolation, peer/caller lifetime, OS-user data-root access and absence of an accidentally reachable private socket. Spawning a process is not proof of protected IPC; same-user malware remains outside a process-boundary guarantee.

## Cryptographic custody and recovery design

**Client-held encrypted security space.** Each space has an independent high-entropy content key *epoch* generated and controlled on an authorized client, never stored in decryptable form by the synchronization host. Encrypt/authenticate each stored version and its bound context using vetted AEAD/envelope primitives; bind collection identity, class, object identity, version and key epoch into authenticated context, with explicit nonce-uniqueness and tamper/rollback handling. Use distinct secret material for authentication, encryption and recovery. Key material is protected by a verified OS-backed credential facility on enrolled endpoints; an authorized recipient receives only a properly authenticated, recipient-wrapped collection key. Client code must validate ciphertext and authenticated metadata **before** indexing or displaying it, including after an untrusted server reorders or replays valid old objects. A malicious server can still suppress changes; freshness needs durable trusted client state and explicit reset/rebootstrap safeguards.

The owner must be offered independent, offline-verifiable recovery material at enrollment, with a tested restore into a new authorized device and clear confirmation of how it is protected. An identity-provider password reset or server administrator must **not** unlock a client-held collection. If *all* client keys and valid independent recovery material are lost, **the ciphertext is unrecoverable**; do not implement an invisible server escrow or pretend a recovery button can restore inaccessible keys. Recovery-key creation, envelope/key-epoch format, device approval and rotation are implementation deliverables of #15 and #40, not completed here.

**Trusted-host processing space.** Its specifically approved host holds recoverable decrypting authority in a protected key/secret facility separate from ordinary records and logs; encrypted at-rest storage and backups, restricted operator access, rotation/compromise response and verified restore are required. This is not E2EE. If an operator can read plaintext in memory, disk encryption does not revoke that capability. A trusted host may not transitively grant cloud providers or unrelated agent tools disclosure rights.

**Local-only space.** A present local catalog/backup is plaintext; restricted filesystem access, hashes and SQLite snapshots do **not** provide encrypted-at-rest, hostile-user integrity or secure offsite recovery. Separate optional device/backup encryption must be explicitly implemented and measured rather than inferred from this classification.

**Availability and recovery.** Minimize loss of committed acknowledged data while defining an honest, deployment-specific RPO/RTO, acknowledgment/replication policy and independent encrypted backup/restore. A single powered-off device cannot provide a zero-loss multi-site guarantee or unattended remote agents. Backups must include content, source/revision/event and key-recovery dependencies appropriate to their class; a ciphertext backup without keys cannot restore plaintext. Restoration must prove object authenticity/consistency, account/collection isolation, protected secrets and version compatibility. Physical faults, interrupted key rotations, host compromise and loss of the last recovery factor are negative acceptance cases for #15/#40/#41.

## Processing, inference and authorization

Derived extracts, index entries, embeddings, search results, excerpts, cached responses, model prompts, exported archives and audit receipts inherit the source's authoritative security-space scope and disclosure policy. The **execution layer**, not a model, checks principal, resource, operation, expiry, membership and requested destination before every data disclosure or side effect; source revocation invalidates derived access. No shared cache whose key omits authorization context. An agent that runs remotely can work only on authorized trusted-host collections and specifically permitted tools; client-held content cannot be silently decrypted for it while devices are offline.

Local inference is distinct from external inference. Owner-approved CLI verification already implements a separate selected/redacted outward payload; that approval is **not** permission to send other sources or to use a fallback remote provider. A future browser client, browser extension or MCP integration requires its own scoped transport/authentication review; a local web listener is not authenticated merely because it binds loopback. [ADR 0021](0021-owner-local-caller-security.md) continues to prohibit ordinary browser-origin access to the owner-local integration API by default.

The local note/archive identity in #14 remains stable through export/import, but legacy portable ZIP and current local snapshots are plaintext and are not a key-wrapped synced collection. [ADR 0006](0006-versioned-sync-protocol.md) remains authoritative for versioned expected-revision writes, operation receipts, tombstones, cursors and conflict outcomes. A ciphertext-only service may validate visible opaque revisions and authorization but **must not claim it validates hidden plaintext path collisions or content-link semantics**; enrolled clients are responsible for those checks.

## Deny-by-default release gate

**Today:** `Praxis.Api` registers only `/health/live`; current automated HTTP tests prove representative private routes absent, *not* authentication, encryption, bound network interfaces or OS-user separation. The first-party macOS worker's access to a selected local catalog is not a network sync service.

**Before remotely reachable private data:** #13's reviewed [threat model](../security/threat-model.md) and [security test matrix](../testing/remote-trust-security.md), #15 identity and key lifecycle, #19 authorized durable transport, #40 encrypted/verified recovery and #41 secured deployment/observability must satisfy their **actual** negative and fault tests. No private route is enabled because #50 is closed or this ADR is accepted. #32 separately governs agent approvals, executions and audit. Tests with only memory fixtures, liveness-only HTTP or unexecuted CI cannot satisfy those gates.

## Reference standards and limitations

Use [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) for OAuth token/code hardening when OAuth is selected; [NIST SP 800-63-4](https://csrc.nist.gov/pubs/sp/800/63/4/final) for applicable authenticator lifecycle principles; and [OWASP ASVS 5.0.0](https://asvs.owasp.org/) to map concrete service verification. These are engineering references, **not compliance or assurance-level claims**. No bespoke cryptographic algorithm or home-grown public identity server is authorized by this ADR.
